# Теневой пилот базы мониторинга

Дата: 28.09.2026. Статус: **локальный пилот реализован и проверен**. Этап миграции базы не завершён: сайт продолжает читать прежние витрины, остальные наборы, API, экспорт и бот не подключены. SQLite не выбран production-хранилищем; PostgreSQL остаётся кандидатом для общего сервиса. Размещение и доступы ещё требуют решения пользователя. См. [предварительное архитектурное решение](technology_decision.md).

## Граница реализации

Код: `pipeline/database/schema.sql`, `repository.py`, `import_monitoring.py`; команды: `scripts/import_monitoring_database.py`, `scripts/check_monitoring_database.py`. Новых зависимостей нет: SQLite из stdlib, существующие pandas/openpyxl. Проверенная SQLite 3.45.3; минимум 3.37 из-за STRICT-таблиц. Пилот рассчитан на один writer и локальный файл Windows в WAL, не на сетевой файловый ресурс.

Основная таблица `monitoring_records` содержит типизированные поля РВ/ОКС, застройщика, УИН, адреса, года, назначения/группировки и площадей. Остальные нормализованные значения и исходные ячейки сохранены JSON; это дополнение к типизированной схеме, не EAV и не pickle/BLOB вместо таблиц. В `raw_files` один раз сохранены заголовки листов, в строках — формулы и их cached values. Формулы не вычислялись, внешние ссылки не открывались. Оформление Excel остаётся в исходном XLSX, семантическое содержимое ячеек представлено в JSON с типами. Числовые JSON-ячейки также хранят десятичную строку.

`sources → raw_files → dataset_versions → monitoring_records` фиксируют происхождение. Ключ строки — `(version_id, raw_file_id, source_sheet, source_row)`; `source_record_id` — SHA-256 компактного JSON `[raw_sha256, sheet, 1-based Excel row]`. УИН nullable и nonunique. Корпуса, компоненты и повторные разрешения не склеиваются по УИН или названию. Сумма площади строк не объявляется доказанной площадью уникальных объектов.

Импорт вызывает общий `DataAccess(DataContext(..., use_marts=False)).load_monitoring_2_0(source_path=..., include_provenance=True)`. Происхождение назначается в core до фильтрации/concat; адаптер не повторяет категории и исправление годов. Дополнительное чтение openpyxl сопоставляет физические строки с этой lineage, сохраняет ячейки и восстанавливает NULL основной площади. Обход исторического processed с известной потерей компонентов не используется. Витрина используется только для отдельной сверки.

Версия определяется SHA-256 raw и fingerprint кода нормализации. Повтор с тем же содержимым и кодом идемпотентен; иной результат при той же паре отвергается. Изменение нормализатора создаёт новую версию даже для того же raw. Сначала в одной транзакции записываются/проверяются строки и запечатывается metadata версии; завершённые версии и строки нельзя UPDATE/DELETE/REPLACE или дополнять. `publications/publication_members` формируют публикацию одного набора monitoring. Активный указатель переключается внутри `BEGIN IMMEDIATE` только при совпадении ожидаемых `(publication_id, generation)`; generation предотвращает потерю изменения в сценарии A→B→A. Ошибка до переключения оставляет прежнюю публикацию. Rollback переключает указатель на историческую версию без удаления данных.

Каждый query открывает read-only соединение и фиксирует публикацию в транзакционном snapshot. Для серии запросов вызывающий код может явно удерживать `snapshot()` либо передавать `publication_id`; без этого два отдельных запроса могут правомерно увидеть разные публикации. Чтение не запускает загрузчиков, Selenium или Streamlit.

## Десятичные значения и отсутствие данных

Площади хранятся **TEXT с десятичным числом**, не SQLite REAL. Масштаб переменный, в м²: адаптер не округляет и не умножает на скрытую степень. Контракт допускает до 30 цифр и до 18 знаков после запятой; агрегирование и validation используют `Decimal` с precision 60. В query величины возвращаются строками и сопровождаются `units`. Денежных полей в этом пилоте нет.

В `total_area_m2` и `residential_area_m2` отсутствующие/нераспознаваемые cached ячейки сохраняются NULL, с отдельными missing/invalid-флагами. Нулевое исходное число остаётся нулём. Строка из-за такой ячейки не отбрасывается. Нераспознаваемый текст и формула доступны в raw JSON. Суммы пропускают NULL, но одновременно возвращают их количество; пустой результат содержит `record_count=0`.

Категории площадей сохраняют действующие значения общего loader, включая его zero-fill/clip-политику. Это **производные нормализованные значения**, и query содержит предупреждение об этом. Decimal-хранение не исправляет артефакты ранее выполненной арифметики float в Excel/pandas: например, сохранена категория МОП РВ `20321982.172331000053676`. Подмена этой точности округлённым числом не выполнялась. Равенство roundtrip не доказывает достоверность исходного измерения или аддитивность компонентов.

## Проверки отказов и review

15 групп регрессий на временных базах проверяют: повторный импорт; новый нормализатор того же raw; пустой/повторный УИН; точный Decimal и NULL; пустые/отрицательные/nonfinite/недетерминированные данные; неверную lineage; сбой до указателя; snapshot при конкурентной записи; исторический запрос; CAS/ABA; rollback; одного победителя конкурентных writers; неизменность и SQLite integrity/FK; backup/restore; валидацию query и пустую выборку; 30-значные числа с одинаковой precision validation/SQL. Это не 15 независимых производственных сценариев: некоторые проверки сгруппированы.

Независимый medium review обнаружил обход UPDATE/DELETE guard через `INSERT OR REPLACE` у raw metadata и различие Decimal-context 28/60. Оба исправлены: добавлены INSERT-guards, повторная регистрация raw использует SELECT-ifabsent; validation использует precision 60. Проверены REPLACE, прежний raw с новой версией и большие числа. Повторное review одобрило исправления; root независимо выполнил 15 групп fixtures.

Для реальной базы выполнен SQLite online backup и восстановление через backup API в **новый** файл; integrity/FK и query совпали. Проверены обе реальные публикации; последняя копия `outputs/audit/monitoring.backup.3dcf1139dd1c.sqlite`, восстановленная — `monitoring.restored.3dcf1139dd1c.sqlite`. Существующие файлы не перезаписываются. Это проверка локального механизма, не согласованные RPO/RTO, off-site backup или автоматическое расписание.

Доказательства: `outputs/audit/monitoring_database_checks.json`, `monitoring_database_fixtures.json`, `monitoring_database_independent_fixtures.json`, `monitoring_database_roundtrip.json`, `monitoring_database_load.json`.

## Локальная нагрузка

Замер выполнен в отдельном окне после остановки тяжёлых root-проверок, на первой публикации и одной версии базы. Позднее изменились только guards и precision validation; содержимое строк совпало по SHA-256. Замер не повторялся на базе с двумя версиями.

| Потоков-читателей | Запросов | Медиана, с | p95, с | Максимум, с | Ошибок |
|---:|---:|---:|---:|---:|---:|
| 1 | 20 | 0.126 | 0.213 | 0.224 | 0 |
| 5 | 25 | 0.605 | 1.189 | 1.284 | 0 |
| 20 | 100 | 2.418 | 4.937 | 5.096 | 0 |

Нагрузка — Python ThreadPool, отдельное read-only соединение на запрос, фиксированная публикация, выбор всех/РВ/ОКС/года/застройщика; каждый ответ включает точные суммы и 50 строк. p95 — nearest rank по указанному N. Кэш ОС/SQLite смешанный; сборка соединения, Python Decimal aggregate и сериализация строк включены. Это не HTTP, не одновременные браузеры, не экспорт и не нагрузка на production-историю. RAM не измерена этим тестом. Уже при 5 читателях p95 превышает ориентир 1 с; при 20 — 4.94 с. Для общего сервиса потребуются агрегаты/кэш и отдельное сравнение PostgreSQL; текущий результат не подтверждает production SLA.

## Контракт чтения и воспроизведение

```python
from pipeline.database import MonitoringDatabase

db = MonitoringDatabase("outputs/audit/monitoring.sqlite")
response = db.query(filters={"registry": "rv", "year_from": 2022}, limit=100)
# Последующая страница должна явно использовать ту же публикацию:
next_page = db.query(publication_id=response["publication_id"],
                     filters=response["filters"], limit=100, offset=100)
```

Ответ содержит `publication_id`, `version_id`, `filters`, `limit/offset`, `units`, `grain`, `provenance` (raw hash, версия нормализатора, время локальной публикации, source dates), `quality_warnings`, `summary`, `rows`. В каждой строке есть sheet/Excel-row/source-record ID. Разрешены только именованные фильтры; значения передаются параметрами SQL. `source_published_at=null` отличает неизвестную дату источника от времени публикации нашей БД. Локальное read-only соединение не заменяет авторизацию конечного пользователя.

```powershell
python scripts/import_monitoring_database.py data/raw/realty/nashdom/monitoring_2_0_20260717.xlsx --publish
python scripts/check_monitoring_database.py --source data/raw/realty/nashdom/monitoring_2_0_20260717.xlsx --skip-load
python scripts/check_monitoring_database.py --verify-existing --output outputs/audit/monitoring_database_roundtrip.json
python scripts/check_monitoring_database.py --load-only --output outputs/audit/monitoring_database_load.json
```

Без `--publish` importer только создаёт проверенную версию. Для rollback: получить `expected = db.active_state()` и вызвать `db.rollback(старый_publication_id, expected=expected)`; при чужом переключении требуется повторно прочитать/оценить состояние, а не молча перезаписывать его. Для backup — `db.backup(новый_путь)`, восстановление — `MonitoringDatabase(путь_backup).backup(новый_путь_восстановления)` с последующей проверкой.

Открыты: PostgreSQL/размещение, схема остальных наборов и миграции, серверные права/auth, общий сервис и равенство сайт/API/бот, экспорт/jobs, свежесть, календарь публикаций, retention, наблюдение в эксплуатации и физическая мобильная приёмка. Следующий крупный этап не запускался.
