# Базовый снимок профиля застройщика

## Назначение и границы

`frontend/public/profile-snapshot.json` содержит замороженные реальные данные
для визуального прототипа. Это не API и не новый расчётный контур.
`scripts/build_dashboard_snapshot.py` использует напрямую `DataAccess` и явный
`DataContext`, без импорта Streamlit и фасада `app.data_access`.
Целиком прочитаны `app/pages/7_Профиль_застройщика.py` и `pipeline/data_access.py`.

Профили: `пик:msk`, `пик:rf`, `самолет:msk`, `самолет:rf`, `capital group:rf`.
Названия действительного селектора: ПИК, САМОЛЕТ, CAPITAL GROUP. У Самолета
совпадают короткое и длинное юридическое имя; оба учитываются существующей
нормализацией. Capital Group в квартирографии найден только по РФ:
московский вариант не придуман.

**Регион меняет только квартирографию.** Структура, годовой ввод, таблицы
объектов и эскроу остаются московскими. Рейтинги и распроданность одновременно
содержат Москву и РФ. `otherRf` в переносах означает **РФ минус Москва**.
Ограничения карты, координат, подтипов, финансирования или только жилья
не добавлялись. Таблицы объектов не сэмплируются.

Реальные исполняемые разделы важнее устаревшего вступительного описания
страницы: сейчас четыре структурных donut-блока, три сравнения жилой площади
и шесть карточек переносов. Новая годовая диаграмма переносов не добавлялась.

`provenance` содержит относительные пути, размеры, SHA-256, UTC-время
изменения, исходные токены `DataAccess.data_version`, попытки чтения витрин,
реально открытые входы, версии библиотек и хеши расчётного кода.
`openedInputs` включает отклонённые файлы: открытие не означает вклад в метрики.
До и после извлечения проверена неизменность входных файлов и их версий.
Raw-файлы и витрины не перезаписывались.

## Соответствие разделов

| Раздел страницы / поле JSON | Источник и существующее правило |
|---|---|
| Рейтинги / `ratings` | Первая совпавшая нормализованная строка. Строительство: `obyem_stroitelstva`; накопленный ввод: `nakopl_vvod`, не годовой `obyem_vvoda`. Оценка: строительство РФ, накопленный РФ, строительство Москвы, накопленный Москвы. |
| Москва и другие регионы / `housingComparison` | Одинаковые календарные годы: карточки `Сдано_YYYY_м²_num` РФ минус РВ `category_жилое` Москвы. Для каждого года нужны положительное РФ, московские строки и `0 <= Москва <= РФ`. |
| Три donut ввода / `categoryDonuts[0..2]` | Все РВ компании, включая исторические листы; годовые блоки фильтруются равенством году. Последний год определяется всем monitoring, не только компанией. |
| Годовой ввод / `annual` | Groupby года РВ. График 2022..максимальный год компании, отсутствующие годы заполнены нулями. Левая сводка только >=2022; `allYears` сохраняет ранние входы. |
| Строительство / `categoryDonuts[3]` | ОКС: `Статус РС=Действует` И `Ввод в эксплуатацию=В строительстве`. Если этих колонок нет, fallback `Статус объекта=Строящийся`. Три отображаемые категории. |
| Распроданность / `rasprod` | Последняя строка компании листа `developers` по `year,month`, независимо для Москвы и РФ. Отношение читается из источника, не пересчитывается. |
| Типы квартир / `apartments` | Первая региональная строка `developers`. Per-dev принимается только при `total>0` и строгом `abs(perDev/aggregate-1)<0.05`; иначе количество типа = агрегат * доля / 100, площадь типа неизвестна. |
| Переносы / `delays.cards` | Московские знаменатели из `Общая площадь` monitoring; другие регионы через разность РФ/Москвы одного источника ЕРЗ. Исторические региональные суммы только по парным годам. |
| Эскроу / `escrow` | Все московские строки компании. Доля остатка = долг/кредит, покрытие = выручка всех площадей/долг, не выручка/кредит. |
| Реестр РВ / `objects.commissioned` | Все строки компании; год ввода вниз, общая площадь вниз. |
| Все ОКС / `objects.permitted` | Все строки, включая введённые и планируемые; статус вверх, общая площадь вниз. Активный фильтр donut здесь не применяется. |

Категории вычисляет исходный загрузчик. РВ: жилое = жилая площадь при
`Отрасли=Жилые объекты` и `Группировка=Жилье`; МОП = положительная разность
общей и жилой в тех же строках; нежилье в жилье = общая площадь при жилой
отрасли и `Группировка=Нежилье`; отдельное нежилье = общая площадь других
отраслей. ОКС использует только `Назначение`: жилье даёт жилое и МОП,
нежилье целиком идёт в отдельное нежилое. Подтип не участвует.

## Контракт JSON

`schemaVersion=1`. Поля верхнего уровня: `generatedAt`, `sourceDates`, `schema`,
`controls`, `provenance`, `profiles`, `verification`, `contentSha256`.
Встроенный `schema` описывает поля и единицы. Основной контракт frontend:

- `profiles[]`: `id`, `developer`, `developerKey`, `region`, `controls` и разделы.
- `categoryDonuts[]`: `id,title,region,years,status,rowCount`,
  `segments[{key,label,valueM2,displayThousandM2}]`, `totalM2`, `displayTotalThousandM2`.
- Ключи категорий: `residential`, `common`, `nonresidentialInHousing`,
  `standaloneNonresidential`. Строительство показывает первую, вторую и четвёртую.
- `annual.rows[]`: `year,valuesM2,totalM2`; `allYears` и `legend` отдельно.
- `ratings.rows[]`: `id,title,rf,msk`; региональные ячейки `place,displayPlace,row`.
- `rasprod.msk/.rf`: `period{year,month}`, `values{soldPercent,readinessPercent,ratioPercent}`,
  `display`, `row`, `columns`.
- `apartments`: `totalCount,totalAreaThousandM2,averageAreaM2,marketSharePercent`,
  `rows[{type,count,sharePercent,areaThousandM2}]`, `display`, исходные строки,
  `perDevAccepted` и `sourceNote`.
- `housingComparison[]`: `years,segments,totalM2,status`; территории `msk/otherRf`.
- `delays.cards[]`: `id,region,title,valueM2,baseM2,percent`,
  `displayValue,displayBase,displayPercent,sourceNote`; операнды в `inputs`.
- `escrow`: `region=msk`, `loanRub,debtRub,revenueRub,debtSharePercent,coveragePercent`,
  `display,columns,rowCount`.
- `objects.commissioned/.permitted`: `columns,rows,rowCount`; все исходные строки.

Только конечные JSON-числа; неизвестное, NaN и Infinity становятся `null`.
`display*` сохраняет округления и прочерки страницы. Нули загрузчика не
доказывают исходный ноль: monitoring заполняет нечисловые площади нулями,
карточки ЕРЗ так же преобразуют пустые ячейки. Нулевые ячейки таблицы типов
страница показывает пустыми, поэтому в её JSON-строках они равны `null`.
Пустой donut имеет `noData` и неизвестный итог, не выдуманный наблюдаемый ноль.

## Воспроизведение и проверки

Из корня репозитория в PowerShell:

```powershell
$env:PYTHONIOENCODING = 'utf-8'
python -X utf8 scripts/build_dashboard_snapshot.py --check
python -X utf8 scripts/build_dashboard_snapshot.py --check --verify-page
```

`--check` ничего не записывает: берёт существующий `generatedAt`, повторяет
извлечение и сравнивает все байты. Явная регенерация:

```powershell
python -X utf8 scripts/build_dashboard_snapshot.py --generated-at '2026-10-07T12:30:32+00:00'
```

Для побайтового воспроизведения должны совпадать входы, их metadata,
расчётный код, библиотеки, режим загрузки и время. Выбор по `mtime`, проверки
витрин и fallback оставлены существующему DataAccess. Native-токены версии
включают `ctime`/идентификаторы файлов: после переноса на другую машину
равенство metadata не обещается даже при совпадающих SHA-256 входов.

Выполненные проверки:

- Первая сборка: 5 профилей, 66 файлов, 80 AST-сравнений с чистыми функциями
  исходной страницы. Хеш `e7c1df10df4227cfac3bb4c8d58048403e02033c82f6a578ff0993537d3502fc`.
- Повторный `--check` дал точное побайтовое совпадение первой сборки;
  родительская задача отдельно подтвердила эту проверку.
- Добавлен и выполнен `--verify-page`: весь исходный код страницы с исключёнными
  imports, явными core-данными и перехватчиком UI. Для пяти профилей совпали
  9 KPI, 3 таблицы, данные donut/годовых диаграмм, операнды и подписи шести
  карточек переносов, значения распроданности.
- Финальная регенерация с прежним временем прошла `--verify-page`.
  Данные и схема не изменились; хеш кода в provenance обновился. Итоговый
  `contentSha256 = ee427c3e6fe27d8a11cdc7d562ce6cd033e15c7ab01fd40c6559151cfe0822aa`.

`contentSha256` вычисляется по каноническому содержимому без самого поля хеша;
время и metadata включены. Это не хеш форматированных байтов JSON.
80 AST-проверок встроены в каждую сборку. Полный перехват страницы запускается
только с `--verify-page` и требует Plotly.

Эти проверки не доказывают достоверность upstream-источников, исправность
старых витрин, весь диапазон компаний или полную браузерную/интерактивную
паритетность. Браузерная интеграция и независимое ревью принадлежат
родительской задаче. Изменены только builder, JSON-снимок и данный документ;
коммит не создавался.

## Подключение API после согласования

Расчёты механически вынесены из builder в `pipeline/profile_calculations.py`;
сам builder и API используют один модуль. Все пять API-профилей совпали с данным
эталоном после выравнивания канонического написания названия компании. Реестры,
числа, единицы, пропуски и display-поля сравниваются целиком. API не ограничен
этими пятью профилями; паритет остальных компаний ещё не сертифицирован.

Frozen JSON регенерирован с тем же `generatedAt`; значения и источники не
изменились, изменены только provenance кода и производный хеш:
`5e6a83d340e3076af5347e4bdbf2648e1a700aaf25e392121308b4ca83c2d334`.
`--check` и `--verify-page` выполнены успешно после извлечения общего модуля.
